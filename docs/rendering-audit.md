# 렌더링 코드 평가와 개선

메인 앱(`index.html`, `lib/inside/`)의 렌더링 코드와 최적화를 평가하고, 평가에서 확인한 문제를 고친 기록입니다. 렌더 루프·품질 예산·자원 해제·컨텍스트 복구는 이미 잘 설계되어 있었습니다. 실제 병목은 첫 로딩 경로(모듈 구성·이미지 인코딩)와 몇몇 GPU 작업의 시점에 있었고, 시나리오 투명도 처리에서 화면이 틀리게 그려지는 버그가 하나 있었습니다.

## 측정 환경

- Chromium 141(Playwright), WebGL은 SwiftShader(소프트웨어)입니다. GPU 처리 시간과 FPS는 실제 기기와 다르므로 셰이더 링크·텍스처 업로드는 **횟수와 용량**으로만 비교합니다.
- 첫 로딩은 GitHub Pages와 비슷하게 gzip·`Cache-Control: max-age=600`·ETag를 주는 정적 서버에서, Lighthouse 모바일과 같은 조건(RTT 150ms, 1.6Mbps, CPU 4배 감속, 390×844·DPR 3)으로 측정했습니다.
- 변경 전 수치는 같은 환경에서 변경 전 커밋(`f187b1b`)을 별도 작업 트리로 띄워 측정했습니다.

## 확인한 문제와 변경

### 1. 시나리오 페이드·고스트가 불투명하게 그려짐

Three.js r170은 `transparent=false`인 재질의 셰이더에 `#define OPAQUE`를 넣어 알파를 1로 고정합니다. 실행 중에 `material.transparent`만 바꾸면 `needsUpdate` 없이는 셰이더를 다시 고르지 않아, **처음 그려질 때의 상태가 굳습니다.** `#story/music/6`에서 5로 이동하면 스피커 외함 재질 17개가 불투명도 0.155인데도 `OPAQUE` 셰이더로 그려져, 증폭 회로 기판이 가려졌습니다. `#story/music/4`로 바로 들어오면 정상이라 진입 경로에 따라 달라지는 버그였습니다.

- `scenario-mechanisms.js`의 `commitTransparency()`가 렌더 직전에 실제로 바뀐 재질에만 `needsUpdate`를 설정합니다. 한 프레임 안에서 페이드와 고스트가 값을 번갈아 바꿔도 최종 상태만 반영합니다.
- `prepareBlended()`가 반투명 변형 셰이더를 시나리오 진입 전에 컴파일합니다. 첫 페이드가 스크롤 도중에 셰이더를 링크하지 않습니다.
- 결과: 같은 경로에서 오래된 셰이더로 그려지는 재질 17개 → 0개입니다. 출시 상태 화면과 강제로 셰이더를 갱신한 화면의 차이도 0픽셀입니다. 키보드 페이드아웃(`typing`)도 55개 → 0개입니다.

### 2. Wiki가 3D 코드 전체를 기다림

`site.js`가 부품 보기·시나리오·관계지도·Wiki 진입 비행 모듈을 정적으로 import해, `#wiki`로 들어와도 Three.js(675KB)와 관계 데이터(148KB)를 포함한 42개 스크립트(gzip 383KB, import 깊이 9)를 모두 받아 평가해야 목록을 그렸습니다. `study.js`의 Three.js 동적 import는 그래서 효과가 없었습니다.

- 네 화면을 `site.js`에서 동적 import로 바꿨습니다. 주소로 직접 들어오면 해당 모듈을, 링크를 가리키거나 누르면 그 화면의 모듈을, 페이지가 한가해지면 부품 보기·시나리오 모듈을 미리 불러옵니다. 데이터 절약 모드와 2G·3G 연결에서는 미리 불러오지 않습니다.
- `build_inside_manifest.py`가 첫 화면 모듈 19개(gzip 71KB)를 `modulepreload`로 미리 요청하게 합니다. import map을 `<head>`로 옮겨 본문을 해석하기 전에 요청을 시작합니다. 포스터 배치에 쓰는 두 모듈만 `<link>`로 두고, 나머지는 짧은 경로 스크립트가 주소에 따라 추가합니다. Wiki·부품 보기·시나리오·관계지도로 직접 들어오면 해당 화면의 모듈 묶음과 함께 곧바로 요청하고, 필름 시작 주소에서는 시작 포스터가 도착한 뒤 필름 모듈과 함께 요청해 포스터가 연결을 혼자 쓰게 합니다. 모든 주소에서 첫 화면 모듈을 곧바로 받게 하면 무손실 포스터와 대역폭을 나눠 `#home` LCP가 약 0.2초 늦어졌습니다.
- 자산 URL 목록(`assets.js`)을 메인 페이지에 인라인했습니다. 모든 경로에서 파서를 막던 요청이 하나 사라졌습니다.
- CPU 시작 이미지는 필름 시작 주소(`#home`·`#journey`)에서만, `<head>`에서 스타일보다 먼저 요청합니다. 예전에는 `#wiki`에서도 숨은 포스터를 높은 우선순위로 받았습니다.
- `hero.js`의 금속 결 텍스처(1024², 선 7,200개)는 첫 모델을 만들 때 생성합니다. 모듈을 불러오기만 해도 67ms(CPU 4배 감속 286ms)가 들던 작업입니다. 관계지도 iframe은 자원 해제 함수를 `dispose.js`에서 가져와 모델 생성 코드를 더 이상 불러오지 않습니다.

### 3. 무손실 부품 이미지

목록·상세 부품 이미지 24장은 1152×864 무손실 WebP였습니다(합계 1,731KB).

- `tools/build_inside_images.py`가 무손실 렌더(`assets/models/redesign`)에서 손실 WebP(q88)를 1152px와 576px 두 가지로 만들고, 목록은 `srcset`·`sizes`로 휴대폰 칸에 576px 판을 씁니다. 1,731KB → 655KB(1152px)·321KB(576px)입니다. 576px 판도 마스터에서 줄여 두 번 압축하지 않습니다. 목록 배경 위 평균 오차는 약 0.3/255입니다.
- CPU 시작 이미지(데스크톱 182KB·모바일 56KB)는 무손실로 둡니다. 첫 실시간 프레임과 픽셀 단위로 같아야 전환이 보이지 않고, `test_visual_continuity.py`가 평균 오차 0.1/255 미만을 확인합니다(저장소 기록 0.0, 이 환경의 데스크톱 0.003). q90 손실 압축은 데스크톱 37KB로 줄지만 평균 오차가 0.61이 되어 이 기준을 넘고, 무손실 최대 압축은 0.5%만 줄었습니다.
- `build_room_previews.py`는 무손실 마스터에서 관계지도 이미지를 만듭니다. 두 번 압축하지 않습니다.
- Wiki로 직접 들어올 때만 첫 두 부품 이미지를 `fetchpriority="high"`로 즉시 요청합니다. 다른 경로에서는 숨은 목록이 필름과 경쟁하지 않도록 지연 로딩을 유지합니다.

### 4. 필름 장면이 처음 나타날 때 셰이더·텍스처 처리

CPU만 있을 때 한 번 셰이더를 준비하고, 이후 부품은 처음 그려지는 프레임에서 셰이더를 링크하고 텍스처를 올렸습니다. 조립 완료 6초 뒤에 스크롤을 시작해도 스크롤하는 동안 링크 22회, 텍스처 할당·업로드 102건(밉맵 제외 약 64MB)이 발생했습니다. 그중 스크롤을 시작할 때 모니터 장면을 준비하는 작업(링크 14회, 업로드 10건)은 설계대로이며 변경 전후가 같습니다.

- `study.js`의 `warmComputer()`가 조립이 끝난 뒤 메인보드·온보드 부품·GPU·메모리 순서로, 재질 하나 또는 텍스처 하나씩 유휴 시간에 준비합니다(`requestIdleCallback`, 600ms 제한). 시나리오·부품 보기·관계지도가 무대를 빌려 쓰는 동안과 Wiki에서는 기다립니다. 빌린 쪽은 조명 구성이 달라, 필름 조명으로 컴파일하면 그쪽 셰이더를 밀어내기 때문입니다.
- `preparePrograms()`는 준비가 끝난 셰이더의 uniform을 미리 읽습니다. 첫 그리기 비용이 줄고, 준비했지만 그려지지 않은 변형도 셰이더 객체를 남기지 않습니다.
- 결과: 같은 조건에서 스크롤 중 작업은 모니터 준비분(링크 14회, 업로드 10건)만 남고, 부품 장면에서 생기던 링크 8회·업로드 92건이 0건이 되었습니다. `KHR_parallel_shader_compile`이 없는 환경에서는 링크가 한 단계 안에서 동기적으로 실행되므로, 사용자가 곧바로 스크롤하면 일부는 예전처럼 처음 그릴 때 처리됩니다.
- 이 환경(ANGLE·SwiftShader)에서는 링크와 업로드가 없어도 부품 장면이 처음 그려지는 프레임이 여전히 길었습니다(변경 전 GPU 장면 1.8초, 변경 후 1.5~4.0초). 그 프레임에는 링크·업로드 호출이 없으므로 그 밖의 그리기 시점 작업이지만, 정확한 원인은 확인하지 못했습니다. 실제 GPU에서의 체감 효과도 측정하지 못했습니다.

### 5. Wiki 진입 시 동기 WebP 인코딩과 숨은 필름 캔버스

- `captureCinema()`는 마지막 장면을 `toDataURL('image/webp')`로 인코딩했습니다(2160×1350에서 213~262ms). 이제 2D 캔버스에 복사(1ms)해 그 캔버스를 비행 배경으로 쓰고, 비행이 끝나면 버퍼를 바로 놓습니다. SwiftShader에서 클릭 직후 Long Task는 11.4초 → 6.3초였습니다.
- Wiki 목록에서는 보이지 않는 필름의 그리기 버퍼(DPR 2 데스크톱 2160×1350, MSAA 포함)가 그대로 남았습니다. 이제 비행이 끝나거나 바로 Wiki에 들어오면 1×1로 줄이고, 필름·부품·시나리오로 돌아갈 때 복구합니다.

### 6. 메모리와 반복 업로드

- `disposeCollectionModel()`(`dispose.js`)이 `InstancedMesh.dispose()`를 호출해 인스턴스 행렬 버퍼를 해제합니다. 시나리오 5개·부품 3개·Wiki를 한 바퀴 돌 때마다 늘던 GL 버퍼 12개가 0개가 되었습니다.
- USB 썸네일 아틀라스(4800×2400, 413KB, 디코딩 약 44MiB)는 호버가 가능한 기기에서만 화면 근처에서 받습니다. 터치 기기에는 첫 프레임 정지 이미지(17KB)를 보여 주고, 키보드 포커스로 미리보기를 요청할 때만 아틀라스를 받습니다. 정지 상태 화면 차이는 최대 5/255입니다.
- 시나리오 모니터 화면(960×540)은 카메라 밖에 있을 때 다시 그리거나 올리지 않습니다. 설명 패널(720×390)은 내용이 같으면 다시 그리지 않고, 모바일에서는 이동 중 24Hz로 제한합니다. 동작 줄이기 설정에서는 한 프레임에 멈추므로 화면·패널 모두 그리기를 미루지 않습니다. 예전 화면 제한은 이 설정에서 미룬 그리기를 다음 입력 전까지 반영하지 못했습니다.
- 키보드 자판 글자 44개를 텍스처 하나로 그립니다. 업로드 44회 → 1회, 데스크톱 텍스처 메모리 약 12MB → 3MB이고, 정적 메시를 병합하는 필름의 모니터 장면에서는 글자 그리기 호출도 44회 → 1회로 줄었습니다.

### 7. 필름 캔버스 해상도

필름은 DPR 상한(데스크톱 1.5)만 있어 1920×1080 CSS·DPR 2 화면에서 2880×1620(470만 픽셀), 5K 화면에서 830만 픽셀을 MSAA로 그렸습니다. `quality.js`의 `filmPixelRatio()`가 **420만 픽셀**을 넘지 않게 DPR을 낮추고, CSS 해상도 아래로는 내리지 않습니다. 1440×900·DPR 2 노트북(2160×1350)과 DPR 1 화면은 그대로입니다.

모바일 DPR 상한 1과 프레임 시간에 따른 실시간 해상도 조절은 **바꾸지 않았습니다.** 해상도를 올리면 휴대폰의 GPU 부하·배터리·발열이 늘어 실기기 검증이 필요하고, 실행 중 해상도를 바꾸면 화면이 한 번 흐려지거나 선명해지는 변화가 생깁니다. 이 저장소의 측정은 소프트웨어 WebGL에서 이루어져 프레임 시간 기준이 항상 낮은 해상도로 떨어지므로, 기록된 결과와 비교할 수도 없게 됩니다.

  - `test_mobile_wiki_arrival.py`는 Wiki에 도착한 뒤 필름 버퍼가 1×1인지, 필름으로 돌아가면 바뀐 화면 높이(760)로 복구되는지 확인합니다. 예전에는 Wiki에서도 760을 기대했습니다.
  - `test_wiki_return_edges.py`의 느린 이미지 경우는 576px 판 요청도 붙잡습니다. 이 화면 크기에서 브라우저가 576px 판을 고르므로, 예전 주소만 붙잡으면 느린 경우가 재현되지 않습니다.
  - `test_mobile_navigation.py`는 화면 크기 변경 직후의 진행 상태를 같은 작업 안에서 확인합니다. 따로 확인하면 앞선 이동이 끝나며 생긴 `scrollend`가 먼저 처리되어 속도 제한이 정상적으로 풀립니다. 이 순서 경쟁 때문에 변경 전 코드도 4회 중 2회, 변경 후에는 4회 모두 실패했고, 두 경우 모두 앱 동작은 같았습니다.
- 변경 전 코드에서도 똑같이 실패하는 검사입니다. 이번 변경과 관계없어 그대로 두었습니다.
  - `tests/wiki-arrival.py`: 예전 `design/redesign` 모듈을 버전 없는 주소로 가로채려 해 `__arrival`이 정의되지 않습니다.
  - `tests/scenario-actions.py`: 타이핑 표지의 호버 단계에서 실패합니다.
  - `tests/relationship-integration.py`: `#wiki`로 바로 들어온 뒤 설정되지 않는 `body.ready`를 기다립니다.
  - `tests/scenario-film.py`: 진행값 0.4를 기다리다 시간 초과됩니다.
  - `tests/scenario-extended.py`: 설명 창이 240ms 애니메이션으로 닫히기 전에 포커스를 확인합니다. 1초 뒤에는 변경 전후 모두 `#story-why`로 돌아옵니다.
  - `tests/scenario-usb-cover.py`의 키보드 포커스 단계와 `tools/test_cpu_handoff.py`의 스크린샷 단계입니다. 스크린샷을 뺀 포스터 전환 검사는 변경 전후 모두 통과합니다.
  - `tools/test_visual_continuity.py`: 모바일 시작 이미지가 이 환경의 첫 실시간 프레임과 평균 20.6/255 다릅니다(데스크톱은 0.003). 이 비교만 기록으로 바꾸어 실행하면 나머지 검사(관계지도 진입·복귀 끝점, 오래된 장면 가림, 키보드 배치)는 변경 전후 모두 통과합니다.
