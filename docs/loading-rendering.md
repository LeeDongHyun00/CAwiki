# 문구 없는 로딩과 공간 관계지도 렌더링 개선

작성일: 2026-10-09 (한국 시간). 비교 기준은 `main`의 `7428ff7`이다. 이 변경은 이전 [1차 최적화 기록](rendering-performance.md)에 이어, 새 공간 관계지도와 로딩 연출을 다시 개선한 작업이다.

## 이번에 확인한 병목

새 `#map`은 `relationship-room-study.html`을 iframe으로 연다. 이 파일에는 약 6.75MB의 코드·base64 이미지가 다시 들어 있었다. 메인의 최적화된 모듈 대신 별도의 구형 모듈을 사용했고, 23개 정밀 하드웨어를 한꺼번에 생성·컴파일·렌더했다. 필름을 거쳐 들어오면 부모 WebGL 자원과 iframe 자원이 동시에 남는다. `rAF` 전환 시간만 줄여서는 첫 생성과 GPU 처리량을 줄일 수 없다.

마지막 모니터도 매번 동일한 마지막 메인보드 장면을 새 RTT에 그렸고, 건너뛰기에서도 지나가는 복잡한 장면들을 처음 렌더했다. 초기 실험에서 프로그램 준비를 부품마다 반복하면 오히려 전체 준비 시간이 늘었다. 최종안은 **불변 화면은 미리 렌더하고, 상호작용하는 모델은 필요한 때만 렌더**하는 구조다.

## 최종 반복 측정 요약

같은 로컬 Chromium 조건에서 프로필별 3회 중앙값이다. 준비와 이동 연출을 모두 포함한 관측 시간이며 실기기 수치는 아니다.

| 경로 | 데스크톱 전 → 후 | 모바일 전 → 후 |
|---|---:|---:|
| 모니터 진입 | 7.87 → 2.00초 | 4.09 → 0.81초 |
| 공간 관계지도 진입 | 25.41 → 3.05초 | 11.45 → 2.67초 |
| 게임 시나리오 진입 | 3.76 → 3.33초 | 2.29 → 2.54초 |
| CPU 상세 진입 | 1.69 → 2.30초 | 0.93 → 1.06초 |

관계지도 단일 render의 최대 제출 삼각형은 데스크톱 935,991→92, 모바일 776,401→56으로 감소했다. iframe 누적 압축 응답은 약 4,230→711KiB다. 새 전시용 이미지 23개의 RGBA 환산량은 14.4MiB이며 원본 23개는 87.3MiB다. 이 값은 실제 VRAM 사용량이 아니다.

**모든 지표가 개선된 것은 아니다.** 모니터 이미지를 미리 받으면서 최초 메인 응답 합계는 데스크톱 387→603KiB, 모바일 387→474KiB로 증가했다. 데스크톱 초기 최대 긴 작업도 1,783→1,860ms다. CPU 상세와 모바일 게임 시나리오 시간은 악화됐다. 선택 부품만 컴파일하도록 범위를 줄여도 이번 반복 측정에서는 상세 진입 시간 개선을 확인하지 못했다. 첫 프레임을 기다린 뒤 노출하는 UX를 검증했지만 이 경로의 속도 개선으로 보고하지 않는다. 최종 표에 최소/최대와 악화 수치를 함께 남겼다.

## 로딩 표현

- **첫 필름:** 최초 바탕은 검정이다. 우선순위가 높은 작은 투명 CPU 이미지를 즉시 읽어 보여주고, 실제 CPU 3D가 준비되면 교체한다. CPU가 보이기 위해 전체 컴퓨터를 기다리지 않는다. 이미지가 200ms를 넘겨 도착하면 500ms 동안 드러난다. CPU의 3D 제출 시점과 전체 컴퓨터 완료 시점도 별도 마크한다.
- **모니터:** CPU 준비와 함께 데스크톱/모바일용 고정 보드 이미지를 비동기 요청한다. 스크롤 2%부터 모니터 셰이더·텍스처 업로드를 미리 준비한다. 원래 마지막 보드의 카메라·재질을 사용해 생성한 이미지이며, 화면비에 따른 UV 범위를 보정한다. 3D 모니터와 카메라 이동은 유지된다. 자산 실패 시 기존 실시간 RTT 경로를 사용한다.
- **건너뛰기:** CPU 장면부터 사용할 수 있다. 기존 부품 이미지를 같은 챕터 순서로 빠르게 넘기는 합성 애니메이션을 사용한다. 지나가는 정밀 모델을 전부 처음 그리는 비용을 피한다. 모니터가 준비되기 전에는 진행률 94%를 넘지 않고, 준비되면 실제 모니터로 이어진다. 휠·터치·Escape·다른 경로 이동으로 중단할 수 있다.
- **시나리오/하드웨어 상세:** 200ms 이하는 가림막이나 추가 지연을 만들지 않는다. 그 이상 걸리는 준비에는 검정 가림막을 두고, 첫 실제 프레임을 그린 뒤 밝아진다. 밝아지는 시간은 `clamp(대기시간 × 0.35, 360ms, 1200ms)`이다. 시간이 오래 걸릴수록 조금 느려지지만 끝없이 기다리는 연출은 넣지 않는다.
- **접근성:** 모션 줄이기 설정에서는 카메라/노출 애니메이션을 생략한다. 준비 상태는 `aria-busy`로 관리한다. 화면 이동 취소 시 남아 있는 노출 효과도 함께 제거한다. 준비 문구·스피너는 없다. WebGL 실패 때의 이미지 보기/위키 이동 안내는 오류 복구 기능으로 남긴다.

이미지를 보여주는 시점, 실제 3D 제출 시점, 전체 준비 완료는 서로 다른 지표다. CPU 미리보기 표시를 전체 3D 로딩 완료로 보고하지 않는다.

## 공간 관계지도

1. iframe의 인라인 payload를 제거했다. `lib/inside/room-study.js`와 기존 공용 모듈·자산·품질 설정을 사용한다. 모듈과 iframe HTML은 내용 해시로 캐시 버전을 갱신한다.
2. 전체보기와 주제 이동에는 **투명 이미지 평면을 3D 공간에 배치하는 LOD**를 사용한다. 벽, 공간 좌표, 카메라 이동, 주제 모음, 클릭 영역, 연결 설명은 유지한다. 이 단계의 하드웨어는 정밀 지오메트리가 아니므로 각도에 따라 완전한 3D와 실루엣이 다를 수 있다. 측면 이미지는 읽기 쉽도록 방 안쪽을 향한다.
3. 상세를 선택하면 해당 부품만 실제 3D로 교체한다. 관계 쌍은 최대 2개다. 이미지가 먼저 표시되고 설명은 바로 사용할 수 있다. 다른 주제로 돌아가면 상세 지오메트리·재질·전용 텍스처를 해제한다.
4. 섬네일은 기존 투명 이미지를 알파 경계로 자르고 최대 512px로 줄였다. 전체보기에서 큰 라벨 텍스처나 복잡한 PCB를 만들지 않는다. WebGL 없이도 이미지/상세 설명 탐색이 가능하다.
5. 모바일 DPR은 1, 페이드용 타깃은 긴 변 768px 이하로 제한한다. 모바일 주제 전환에서는 불필요한 다중 알파 패스를 생략한다. 기본 곡면 분할도 줄이고 `?quality=high`는 기존 상세 분할을 유지한다.
6. iframe 제거 직전에 자원을 동기적으로 정리하고, 준비 중 취소/컨텍스트 손실도 검증한다. 전체보기의 DOM 주제 링 움직임은 하드웨어 렌더와 독립적이다.

## 검증과 측정 방법

[성능 비교표](performance/loading-comparison.md), [기능 검사](performance/loading-functional.json), [로딩 UX 검사](performance/loading-ux.json), [소스 해시](performance/loading-source-manifest.json)를 함께 보관한다.

`tools/measure_loading.py` v3로 **각 버전 × 데스크톱/모바일 × 3회**, 총 12회를 측정한다. 기준 소스는 별도 디렉터리에 고정한다. 로컬 gzip 서버, Chromium/SwiftShader, CPU 제한 1배, 데스크톱 1440×900/DPR 1 및 터치 모바일 390×844/DPR 3 조건이다. 앱의 실제 DPR 상한은 별도로 적용된다. 성능 측정끼리 또는 다른 브라우저 테스트와 동시에 실행하지 않는다.

동일 경로: 최초 필름 → 일정 간격으로 18/40/65/88% 스크롤 → 모니터 → 위키 → 공간 관계지도 진입 → 컴퓨트 → 네트워크 → 게임 시나리오 → CPU 상세. iframe 내부에 별도 관측기를 넣고, 준비 완료 및 이동 종료까지 기다린다. 이전 측정 도구처럼 부모 렌더러만 읽어 iframe 비용을 놓치지 않는다. 시나리오/상세는 경로 변경 **전 같은 작업에서** 시작 시간을 기록한다.

지표 해석:

- `elapsedMs`: 준비+연출+측정 완료 확인을 포함한 시나리오 시간이다. 순수 네트워크나 GPU 시간은 아니다. 시나리오/상세의 고정 관측 대기 700ms도 포함된다.
- `longTasks`: 해당 프레임의 50ms 초과 작업 개수·최대·초과분 합계. iframe의 GPU 대기로 생기는 멈춤을 모두 대표하지 않으므로 경과 시간·프레임 간격도 함께 본다.
- `frameP95Ms`: rAF 간격 p95. 정지 구간도 포함하므로 실제 게임 FPS/순수 GPU 시간으로 해석하지 않는다.
- `renders.maxCalls / maxTriangles`: 단일 `renderer.render` 호출의 최대 제출량. 한 프레임의 여러 패스를 합산한 값은 아니다.
- `encodedBytes`: 해당 문서의 누적 압축 응답 본문량. iframe 측정은 iframe 자신의 자원이다. 로컬 캐시를 끈 조건이며 운영 CDN 캐시 이득이나 네트워크 RTT를 입증하지 않는다.
- `jsHeapBytes`: CDP JavaScript 힙. VRAM·브라우저 전체 메모리·OS 탭 종료 원인을 뜻하지 않는다.
- `marks / lcp`: CPU 이미지/3D/컴퓨터/모니터 준비 시점과 관측된 LCP. `cpu-preview-visible`은 이미지 준비 후 스타일 변경 시점, `cpu-visible`은 3D 제출 시점으로 실제 디스플레이 완료 시각과는 다르다. WebGL 캔버스 내용은 일반 이미지처럼 LCP 대상이 아니므로 전환 부드러움 판정에 LCP만 쓰지 않는다.

`loading-iteration-2.json`은 이미지 LOD를 도입한 중간 실험이다. 그 뒤 모니터의 사전 렌더, 기본 곡면 분할, 건너뛰기 합성을 추가했다. 최종 판단에는 `loading-before.json`과 `loading-after.json`만 사용한다. `loading-iteration-3.json`에서 부품 상세가 느려진 원인도 확인했다. Three의 compile은 숨겨진 자식도 방문하므로, 최종안은 상세 모델 그룹만 컴파일하고 기존 장면의 조명을 사용하도록 범위를 좁혔다. 부품별 GPU 준비 실험은 효과가 좋지 않아 최종 코드에 포함하지 않았다.

## 재생성 및 실행

```bash
# 기존 투명 이미지를 변경했을 때 (Pillow)
python3 tools/build_room_previews.py
# 보드 모델/카메라/재질을 변경했을 때 (Playwright + Chromium)
python3 tools/build_monitor_frames.py
# JS/이미지 변경 후 항상 실행
python3 tools/build_inside_manifest.py

python3 tools/test_rendering.py
python3 tools/test_loading_ux.py
python3 tools/test_monitor_visual.py
python3 tools/measure_loading.py --root /path/to/baseline --out docs/performance/loading-before.json
python3 tools/measure_loading.py --out docs/performance/loading-after.json
python3 tools/summarize_loading.py
```

모니터의 사전 렌더/실시간 RTT 비교에서 RGB 평균 절대 차이는 255 척도에서 0.116이었다. 데스크톱→모바일 크기 변경 시 전용 이미지 교체도 통과했다. [시각 검사 기록](performance/monitor-visual.json)과 PNG를 함께 보관한다.

`?live-monitor=1#screen`은 사전 렌더 이미지와 비교하거나 재생성할 때 쓰는 기준 RTT 경로다. 페이지·자산은 정적 파일로 그대로 제공하며 런타임 빌드는 필요 없다.

## 남은 확인

실제 iOS Safari와 중저가 Android에서 왕복, 화면 회전, 절전 복귀, 탭 재로드 여부를 확인해야 한다. 이번 자동화는 모바일 뷰포트/터치를 재현한 소프트웨어 렌더러 테스트이며 실제 기기의 메모리 종료를 완전히 재현하지 않는다. 3D 상세/시나리오 최초 셰이더와 모델 생성의 긴 작업은 별도 개선 여지가 있다. 로딩 연출을 넣었다고 해당 작업 자체가 빨라졌다고 간주하지 않는다. 전처리 geometry·공유 shader/texture, 실제 장치 GPU 추적은 후속 후보이며, 결과표에는 남은 지연과 악화된 수치도 그대로 남긴다.
