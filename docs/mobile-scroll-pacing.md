## 원인과 속도 선택

기존 필름과 시나리오는 `현재값 + (스크롤 목표 - 현재값) × 지수 보간 비율`로 진행했다. 관성 스크롤이 큰 목표값을 전달하면 그 차이에 비례해 순간 속도가 커졌다. 전체 진행률 기준 보간이므로 짧은 장면은 더 빨리 사라진다.

`MobileScrollPacer`는 진행률을 각 장면의 경계 사이 위치로 변환한다. 실제 터치로 시작한 모바일(너비 760px 이하) 스크롤에만 다음 제한을 적용한다.

- **최대 초당 1장면**. 필름은 14개 챕터, 시나리오는 해당 시나리오 단계 경계를 사용한다.
- 지연된 프레임도 한 번에 **장면의 5%**까지만 진행한다. 느린 기기에서는 벽시계 기준 진행 속도가 더 느려진다.
- 표시 중인 장면보다 최대 **0.75장면**까지만 목표를 쌓는다. 초과 관성은 네이티브 스크롤 위치를 보정해 버린다.
- 다시 터치하면 현재 보이는 위치에서 시작한다. 반대로 드래그할 때 앞선 관성 목표를 따라가지 않는다.
- 브라우저 주소창 등으로 화면 높이가 바뀌어도 현재 장면과 속도 제한을 유지한다. 저장장치 경로 변경 시 단계 경계도 갱신한다.

초당 0.75 / 1 / 1.5장면 후보의 짧은 챕터 통과 시간은 고정 120Hz 시험에서 1,333 / 1,008 / 667ms였다. 1.5는 전체 장면이 0.67초에 지나가고, 0.75는 긴 드래그가 지나치게 느려질 수 있어 1을 기본값으로 선택했다. 이 값에서 챕터의 약 20%를 차지하는 진입 구간에 최소 약 200ms를 배정한다. 자연스러움에 대한 설계 기준이며 실사용자 평가로 최적값을 확정했다는 의미는 아니다.

건너뛰기, 단계 버튼, 다시 시작, 주소 이동은 의도적인 이동이므로 기존 동작을 유지한다. 데스크톱과 동작 줄이기 설정도 기존 동작을 유지한다. 로딩 UI는 추가하지 않는다.

## 시험 방법과 한계

`measure_mobile_scroll.py`는 Chromium, 390×844, DPR 3, 모바일·터치 에뮬레이션에서 실행한다. 실제 `touchStart/touchMove/touchEnd`로 느린 드래그·빠른 드래그·역방향 드래그를 보낸다. `momentum-burst`는 빠른 드래그 직후 추가 3,000px 네이티브 스크롤을 주입해 큰 관성 목표를 재현한 스트레스 시험이다. 후자는 실제 휴대전화의 플링 속도를 측정한 값이 아니다.

시작 스크롤 목표와 렌더 진행률이 모두 안정된 뒤 측정한다. 장면 속도와 한 프레임 진행량은 실제 필름·시나리오 렌더 tick에서 기록한다. 별도의 rAF 콜백은 프레임 간격 기록에만 사용한다. 소프트웨어 GPU 환경이므로 여기의 프레임 간격과 Long Task 수를 실제 모바일 성능으로 해석하지 않는다. 이번 수정의 목표는 장면 건너뜀 방지이며 FPS 향상을 주장하지 않는다.

## 재현

```sh
node tools/test_scroll_pacing.mjs
python3 tools/measure_mobile_scroll.py --root /tmp/cawiki-scroll-before --out /tmp/before.json
python3 tools/measure_mobile_scroll.py --out /tmp/after.json --strict
python3 tools/test_mobile_navigation.py --out /tmp/navigation.json
python3 tools/test_wiki_return.py --out /tmp/wiki-return --strict
python3 tools/build_inside_manifest.py
```

비교용 디렉터리는 수정 전 `6c56ac0`의 `git archive`로 만든다. 비교 시험은 브라우저를 하나씩 순차 실행한다.

## 측정 결과

큰 관성 목표 주입(`momentum-burst`) 비교. 각 값은 해당 1회 시험의 최대값이다.

| 장면 | 최대 장면/초: 이전 → 이후 | 한 렌더 프레임 진행량: 이전 → 이후 |
|---|---:|---:|
| 필름 | 14.48 → 1.00 | 1.503 → 0.050장면 |
| 전원이 켜지는 순간 | 10.87 → 0.50 | 1.810 → 0.050장면 |
| 키 하나가 글자가 되기까지 | 10.92 → 0.20 | 2.546 → 0.050장면 |

수정본 12개 입력 시험 모두 초당 1장면 이하 / 한 프레임 0.05장면 이하를 통과했다. 역방향 입력 3개도 모두 반대로 진행했다. 느린 소프트웨어 GPU에서 기본·확장 시나리오는 프레임당 제한 때문에 실제 진행 속도가 1보다 작다. 느린 드래그는 기존 보간을 따르며, 큰 입력을 의도적으로 제한하기 때문에 같은 드래그로 도달하는 거리가 줄어든다.

rAF p95와 Long Task 기록도 JSON에 보존했다. 예를 들어 관성 시험의 기본 시나리오 rAF p95는 약 117 → 267ms였고 Long Task는 21 → 41개였다. 진행을 천천히 보여주어 더 많은 렌더 프레임이 필요하며, 소프트웨어 GPU의 렌더 비용을 줄인 변경은 아니다. 따라서 장면 건너뜀 개선과 렌더 처리 성능을 구분한다.
