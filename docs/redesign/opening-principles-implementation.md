# CPU 시작 화면 · 원리 팝업 · 모바일 Wiki 진입

2026-10-09 구현 및 검증 기록

## CPU 프레이밍

기존 포스터는 화면에 맞춰 한 장의 이미지를 축소했지만 실제 CPU 카메라는 화면 비율마다 거리를 다시 계산했다. 따라서 전체 화면 외의 비율에서 포스터와 첫 3D 장면의 크기·원근이 달랐다.

`cpu-framing.js`가 1440 × 900 기준 카메라와 이미지 표시 크기를 함께 정의한다. 시작 카메라의 위치와 원근을 유지하고 화면의 가로·세로 여유에 맞춰 시야각만 조절한다. CPU가 화면 폭의 75%를 넘지 않으며, 낮고 넓은 화면에서는 높이가 제한한다. 모바일 포스터도 동일한 기준 비율로 다시 렌더링했다.

포스터에서 실제 모델로 전환하는 160ms 동안 첫 자세를 유지한다. 미리 입력한 스크롤은 보존하고 전환 이후 이어간다. CPU 챕터 초반에 기존 분해 장면용 카메라로 부드럽게 연결한다.

검증: 1440 × 900, 980 × 820, 820 × 1180, 1440 × 600, 390 × 844, 320 × 568, 844 × 390에서 포스터와 라이브 CPU 외곽의 최대 차이 1px 이내. WebGL 로드 전 창 크기를 바꾸는 경우도 실제 첫 프레임과 비교했다.

## 원리 자세히

승인된 흑연색 팝업을 실제 16편·118개 장면에 연결했다. 큰 하드웨어 이미지, 현재 장면 제목, 짧은 설명, 자세한 설명, 앞뒤 장면의 흐름을 표시한다. 오른쪽 설명 영역은 모바일에서 이미지 아래로 배치한다.

흐름은 이전·현재·다음 장면 순서이며 실제 배선을 의미하지 않는다. 상대방의 GPU·메모리·화면과 서버의 연산 장치는 이름에 위치를 명시한다. USB 이미지는 해당 시나리오에서 사용하는 동일한 3D 조립체에서 렌더링했다.

네이티브 dialog로 모니터와 스피커보다 앞에 표시한다. X와 Escape로 닫으면 원래 장면과 포커스를 복구한다. 짧은 화면에서는 내부 내용을 스크롤할 수 있고 X는 고정한다. 관계페이지로 이동하는 버튼은 제거된 상태를 유지한다.

## 모바일 필름 → Wiki

원인: `WikiArrival.capture()`가 `quality.compact`인 모든 화면에서 즉시 반환해 전환을 생략했다. 이제 모션 감소 설정·이미지 모드·렌더링 실패일 때만 직접 이동한다.

필름의 12개 모델은 기존 렌더러와 재질·형상을 공유하는 복제 계층으로 움직인다. 각 목록 항목의 실제 위치를 측정해 이동하고 최종 이미지와 교차 전환한다. 화면 밖으로 이동한 모델은 렌더 제출에서 제외한다. 목록 제목과 내비게이션은 모델 도착 뒤 나타난다.

모바일 주소창에 의한 높이 변화는 전환 당시의 CSS 픽셀 좌표를 유지한다. 화면 너비가 바뀌는 회전이나 사용자 스크롤·새 경로 진입은 전환을 정리하고 사용 가능한 목록으로 즉시 복귀한다. 전환 후 캔버스 크기, inert, 임시 요소와 원본 모델 변환이 정상인지 검증했다.

## 재현

저장소 루트를 4173 포트의 HTTP 서버로 실행한 뒤 Python Playwright와 Chromium으로 실행한다.

- `python tools/test_cpu_framing.py`
- `python tools/test_cpu_handoff.py`
- `python tools/test_scenario_principles.py`
- `python tools/test_mobile_wiki_arrival.py`

측정값과 캡처는 `docs/performance/opening-principles/`에 저장한다. 검증 환경은 Chromium의 모바일 터치 에뮬레이션과 소프트웨어 WebGL이며 실제 iOS·Android 기기의 성능 측정을 대신하지 않는다.

배포는 최적화된 `lib/inside/` 분할 모듈과 콘텐츠 해시를 유지한다. `tools/build-pages.py`로 과거 단일 번들 호스트를 덮어쓰지 않는다.
