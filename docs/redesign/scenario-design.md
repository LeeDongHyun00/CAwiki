# 시나리오 리디자인 — 하나의 사건을 끝까지 따라가기

2026-10-08 · `redesign` · 승인된 설계와 구현 기록

[직접 드래그해 보는 모션 시안](../../artifacts/scenario-design.html) · [기존 레퍼런스 관찰](reference-audit.md) · [사이트](../../artifacts/inside-site.html)

승인된 모션 시안을 실제 사이트의 게임·부팅·검색·파일 열기 네 편에 적용했다. 현재 구현은 `scenario-data.js`와 `scenario-film.js`에 있으며 각 시나리오는 6개 장면이다. 파일 열기는 SSD·HDD와 4개 장면의 메모리 캐시 경로를 지원한다. 아래 문서는 설계 의도를 기록하며, 각 구간의 실제 진행값·카메라와 문장은 코드가 기준이다. 모션 시안 파일은 승인 당시 구도를 확인하는 용도로 남긴다.

**방향:** 부품이 무엇인지는 메인 필름이 보여준다. 시나리오에서는 **그 부품 때문에 무엇이 달라지는지**를 보여준다. 화면 전체를 실제 3D 공간으로 사용하고, 사용자의 드래그가 사건의 진행과 카메라 이동을 함께 제어한다.

메인 필름의 INPUT / OUTPUT 전시 장면은 제거했다. 후면 I/O 포트 다음에 메인보드 전체가 이어지고, 키보드와 마우스는 마지막 모니터 장면에 등장한다. 부품 컬렉션과 시나리오에서 필요한 입력 장치는 계속 사용한다.

## 1. 이번에 검토할 결과

- **네 편의 연출 설계:** 부팅, 클릭→화면, 검색, 파일 열기. 아래에 학습 목표·동작 순서·카메라·짧은 화면 문구를 정리했다.
- **대표 모션 시안:** 클릭→화면 한 편을 기존 3D 모델로 직접 드래그해 본다. 마우스 → 메인보드의 CPU·RAM → GPU → 모니터가 하나의 공간에 있다. 입력 경로, 부품 내부 전개, 화면 결과, 역방향 탐색을 확인한다.
- **시안과 구현의 범위:** `#story/...`도 동일한 드래그 연출로 교체했다. 단일 광점은 동작 전달을 나타내며 모니터에는 게임의 움직임, 운영체제 첫 화면, 검색 결과, 열린 이미지가 각각 나타난다. 실제 게임·전기 시뮬레이션은 아니다. 아래에 후속 표현으로 기재한 상태 값·명령 타일·픽셀 생성 과정은 현재 단일 신호 표현에 포함되지 않는다.

## 2. 화면의 기본 문법

| 요소 | 설계 |
|---|---|
| 주인공 | 현재 일을 수행하는 부품 1개, 관계를 보여줄 때만 2개. 메인보드는 위치를 기억하게 하는 배경으로 남는다. |
| 텍스트 | 장면 제목 1줄 + 인과관계 1문장. “다음 상태를 계산하다 / CPU가 메모리의 정보를 읽고 게임 상태를 갱신합니다.”처럼 무엇이 변하는지 적는다. |
| 부품 라벨 | 현재 핵심 관계 1개. `CPU ↔ RAM`처럼 방향을 함께 표시한다. 완성 구현에서는 투영 좌표로 연결하되 모형과 겹치면 안전 영역으로 옮긴다. |
| 진행 표시 | 아래쪽의 얇은 진행선과 최대 6개 짧은 구간. 우측 예고 리스트와 상단 내비게이션은 두지 않는다. |
| 상세 설명 | `원리 자세히 ↗`를 눌렀을 때만 열린다. 배경 장면과 진행도를 정지시키고 닫으면 같은 위치로 돌아온다. 기본 인과관계는 이 창을 열지 않아도 이해할 수 있어야 한다. |
| 종료 | 처음의 행동과 달라진 결과를 같이 보여준다. `다시 보기 ↺`와 `Computer Wiki →`만 남긴다. 다음 시나리오로 자동 이동하지 않는다. |
| 시각 톤 | 흑연색 배경, 무광 외장, 넓은 소프트박스 반사, 읽히는 금속 모서리. 이동 중 배경색 전환은 최소화한다. |
| 신호 표현 | 작은 광점은 전달, 얇은 짧은 펄스는 명령, 작은 타일 묶음은 데이터, 격자는 프레임. 의미마다 형태를 달리하고 색에만 의존하지 않는다. |

EDOLUS에서 확인한 **공간→제품→내부의 규모 변화**와 구간별 이동 밀도를 적용한다. Cactus의 **큰 대상·넓은 여백·요청 시 열리는 설명**을 적용한다. 원본의 로고, 내비게이션, 글자 섞임, 우측 탐색 띠는 가져오지 않는다.

## 3. 드래그와 카메라

### 하나의 진행값

휠·트랙패드·마우스 세로 드래그·터치 스와이프를 `progress 0…1`에 연결한다. 부품 위치, 분리량, 신호 위치, 카메라, 화면 변화는 모두 같은 진행값의 함수다. 아래로 진행했다가 위로 되돌리면 정확히 이전 상태로 돌아간다. 개별 타이머로 분해와 데이터 이동을 따로 재생하지 않는다.

드래그 도중에는 카메라를 자유 회전시키지 않는다. 시나리오의 의미를 따라가는 연출에 입력을 집중한다. 부품의 자유 회전은 별도 부품 보기에 맡긴다. 페이지 스크롤과 동시에 회전하는 충돌을 피한다.

### 한 장면 안의 리듬

1. **맥락:** 출발 부품과 다음 대상의 일부를 함께 본다.
2. **행동:** 버튼이 눌리거나 칩 내부가 열리며 상태가 바뀐다. 카메라는 잠깐 충분히 안정된다.
3. **전달:** 변화가 다음 부품에 닿고 카메라가 따라간다.
4. **결과:** 다음 부품이 반응한다. 출발점이 맥락으로 남아 원인을 잃지 않는다.

시안은 구간의 약 40%를 현재 대상을 보는 데 쓰고 이후에 카메라가 이동한다. 완성 구현에서는 중요한 행동에 더 긴 거리를 배정한다. CPU 상태 갱신·GPU 렌더링은 길게, 이미 이해한 공간 통과는 짧게 둔다. 일정 속도로 모든 부품을 훑지 않는다.

### 매끄럽게 만드는 조건

- 프레임 속도와 무관한 지수 보간으로 스크롤 목표를 따라간다. 초기 후보는 응답 계수 `8/s`; 실제 트랙패드·터치에서 지연감을 보며 조절한다.
- 카메라는 위치와 시선 목표를 함께 보간한다. 대상 중앙을 갑자기 바꾸거나 장면 경계에서 회전축을 바꾸지 않는다.
- 분해는 필요한 껍질만 연다. 작동 원리와 무관한 모든 나사를 날리지 않는다.
- 신호가 떠나는 순간과 도착한 부품의 반응에 명확한 순서를 둔다. 모든 선을 동시에 깜박이지 않는다.
- 핵심 동작을 보는 동안에는 포인터 시차·자동 회전을 끈다. 얕은 심도와 블룸은 다음 대상이나 글자를 가리지 않는 범위에서만 사용한다.
- 스크롤을 멈추면 사건도 멈춘다. 계속 돌아가는 팬이나 반복 입자 때문에 다음 단계를 놓치지 않게 한다.
- 빠르게 넘겨도 정확한 목적 상태를 계산한다. 느리게 끝까지 돌려야만 모델이 결합되는 누적 애니메이션을 만들지 않는다.

## 4. 대표 시나리오 — 클릭이 한 프레임이 되기까지

**학습 목표:** 입력 장치가 그림을 직접 만드는 것이 아니라, CPU가 게임 상태를 바꾸고 GPU가 그릴 내용을 계산해 화면으로 보낸다는 것을 이해한다.

시안의 “클릭”은 장면 속 마우스 버튼이 눌리는 사건이다. 방문자는 드래그로 그 뒤에 일어나는 일을 느리게 펼쳐 본다. 스크롤 자체가 실제 컴퓨터의 입력 처리 속도를 나타내지는 않는다.

| 진행 | 보여줄 일 | 카메라·부품 연출 | 화면 문장 |
|---|---|---|---|
| 0–18% | 마우스 스위치의 변화가 입력 보고서가 된다. | 새 마우스의 버튼·휠·곡면이 크게 보인다. 왼쪽 버튼이 눌리고 작은 신호가 USB 입력 경로로 나간다. | 클릭 한 번이 어떻게 화면을 바꿀까요? |
| 18–36% | OS와 드라이버를 거친 입력을 게임이 읽는다. | 메인보드의 연결 지점을 지나 CPU에 접근한다. 히트스프레더를 필요한 만큼 옆으로 열어 내부를 보인다. | 운영체제가 입력을 전달하고, 게임이 클릭을 읽습니다. |
| 36–55% | CPU가 캐시·RAM의 데이터를 사용해 게임 상태를 갱신한다. | CPU에서 DIMM까지 시야를 넓힌다. 읽기와 갱신 방향을 분리해 짧게 보여준다. 완성 구현에서는 게임 좌표 값의 변화를 작은 상태 표식으로 보여준다. | CPU가 메모리의 정보를 읽고 게임 상태를 갱신합니다. |
| 55–74% | 준비한 명령 버퍼를 GPU에 제출한다. | CPU와 GPU 사이를 이동한다. 이번에는 입력 신호와 다른, 짧은 명령 표식이 경로를 따라간다. | CPU가 준비한 그래픽 명령을 GPU가 실행합니다. |
| 74–92% | GPU가 데이터를 읽고 렌더 타깃을 만든다. | GPU 방열 구조가 열리고 다이·VRAM 관계를 보여준다. 후속 구현에서 기하→채워지는 타일→한 프레임으로 이어진다. | GPU가 장면을 그리고 결과를 VRAM에 기록합니다. |
| 92–100% | 프레임 버퍼가 출력되어 화면이 달라진다. | 시선이 모니터로 이동한다. 화면 속 대상이 실제로 이동해 처음 클릭의 결과가 완결된다. | 완성된 프레임이 출력되고, 클릭의 결과가 보입니다. |

**정확성:** 입력 경로에는 USB 호스트 컨트롤러·드라이버·OS가 있다. RAM은 일을 계산하는 주체가 아니다. GPU의 VRAM 읽기와 쓰기를 한 방향 화살표로 뭉개지 않는다. 출력은 GPU의 디스플레이 엔진과 프레임 버퍼에서 이어진다. CPU와 GPU는 실제로 여러 프레임을 겹쳐 처리할 수 있지만 첫 학습에서는 한 프레임의 관계를 분리해서 보여준다.

## 5. 나머지 세 편의 설계

### 전원이 켜지는 순간

**끝에서 알게 될 것:** 전원을 받은 CPU가 펌웨어로 장치를 준비하고, 저장장치의 운영체제를 RAM에 올린 뒤 실행한다.

| 구간 | 장면과 카메라 | 한 문장 |
|---|---|---|
| 0–14% / 시작 | 전원 버튼 접점에서 PSU로 이동한다. 대기 전원·켜기 요청과 주 전원 활성화를 구분한다. | 전원 버튼이 시스템을 깨웁니다. |
| 14–30% / 준비 | PSU → 메인보드 VRM → CPU. 전원 레일이 안정되고 리셋 해제를 표현한다. | 안정된 전원이 준비되면 CPU가 실행을 시작합니다. |
| 30–47% / 첫 명령 | SPI 플래시와 CPU를 함께 잡고 펌웨어의 명령 흐름을 보여준다. | CPU가 펌웨어로 컴퓨터를 준비합니다. |
| 47–64% / 초기화 | CPU에서 DIMM·핵심 장치로 시선을 넓힌다. 메모리 준비가 끝난 영역만 차례로 반응한다. | 메모리와 장치를 사용할 수 있는지 확인합니다. |
| 64–85% / 불러오기 | SSD의 블록이 RAM으로 이어진다. CPU가 지시하는 경로와 데이터가 옮겨지는 경로를 구별한다. | 부트로더와 운영체제 커널이 RAM에 올라옵니다. |
| 85–100% / 실행 | CPU에서 모니터로 물러나 첫 화면을 보여준다. | 운영체제가 실행되고 첫 화면이 나타납니다. |

펌웨어가 SSD에 있다고 표시하거나 CPU가 SSD의 운영체제를 그대로 직접 실행한다고 표현하지 않는다. ATX 신호 이름, 메모리 초기화 전의 임시 실행 환경, 세부 부팅 단계는 상세 설명으로 둔다. 타이밍은 축약된 대표적인 PC 부팅 흐름이다.

### 검색 한 번의 여정

**끝에서 알게 될 것:** 내 컴퓨터가 만든 요청은 인터넷을 통해 서버에 닿고, 돌아온 응답을 브라우저가 해석해야 화면이 된다.

| 구간 | 장면과 카메라 | 한 문장 |
|---|---|---|
| 0–15% / 요청 | 검색창의 단어가 요청의 내용이 된다. 짧게 키보드와 PC 맥락을 보여준다. | 브라우저가 검색 요청을 만듭니다. |
| 15–32% / 주소·연결 | PC 옆에 DNS 확인 경로가 잠깐 갈라지고 돌아온다. 새 HTTPS 연결 준비를 표현한다. | 주소를 확인하고 안전한 연결을 준비합니다. |
| 32–50% / 전송 | NIC 포트에서 케이블을 따라 출발한다. 규모가 바뀌면서 라우터와 인터넷 경로가 보인다. | 요청이 네트워크를 건너 서버로 갑니다. |
| 50–69% / 서버 | 데이터센터 전체 → 서버 한 대 → 처리 중인 영역으로 연속 접근한다. | 서버가 검색을 처리해 응답을 만듭니다. |
| 69–85% / 응답 | 응답 표식이 내 PC로 돌아온다. 출발 때의 장면을 대응시켜 왕복 관계를 이해시킨다. | 검색 결과가 내 컴퓨터로 돌아옵니다. |
| 85–100% / 표시 | 메모리의 응답 → 브라우저의 구성 → 화면. 결과 글줄이 채워진다. | 브라우저가 응답을 해석해 화면을 구성합니다. |

DNS 조회·연결 수립은 캐시와 기존 연결 때문에 생략될 수 있다. 첫 경로는 캐시가 없는 경우를 기준으로 하고 “이미 연결되어 있다면”은 선택 가능한 짧은 비교로 둔다. 모든 패킷이 한 직선이나 완전히 동일한 귀환 경로를 쓰는 것으로 단정하지 않는다. 암호화된 검색어를 라우터 내부에서 그대로 읽을 수 있는 것처럼 그리지 않는다.

### 파일을 여는 순간

**끝에서 알게 될 것:** SSD/HDD는 보관하고, RAM은 작업할 데이터를 두며, CPU가 내용을 해석한다. 캐시에 있으면 저장장치 읽기가 필요하지 않을 수 있다.

| 구간 | 장면과 카메라 | 한 문장 |
|---|---|---|
| 0–16% / 요청 | 파일 아이콘 선택 → OS의 파일 요청. 완성될 이미지의 빈 프레임이 잠깐 보인다. | 파일을 열면 운영체제가 데이터를 찾습니다. |
| 16–32% / 캐시 확인 | CPU·RAM을 잡고 두 경로의 갈림을 보인다. 기본은 캐시 없음. | 메모리에 없다면 저장장치에서 읽습니다. |
| 32–53% / 저장 | 기본 SSD의 컨트롤러와 NAND를 보여준다. 작은 선택으로 HDD 경로를 같은 구도에서 비교할 수 있다. | 저장장치가 요청한 데이터를 찾아 읽습니다. |
| 53–70% / 전송 | 데이터를 CPU 몸체를 관통시키지 않고 장치→RAM으로 보낸다. | DMA로 데이터가 RAM에 옮겨집니다. |
| 70–86% / 처리 | RAM → CPU 내부 캐시·실행 영역을 크게 본다. 이미지 조각의 형식이 해석된다. | CPU가 메모리의 데이터를 해석합니다. |
| 86–100% / 결과 | 처리 결과 → GPU 출력 → 처음 빈 프레임에 사진이 완성된다. | 파일 내용이 화면에 나타납니다. |

SSD와 HDD를 필수 직렬 경로로 연결하지 않는다. CPU 캐시를 메인보드 위의 독립 SRAM 칩처럼 그리지 않는다. “캐시에 있음”을 선택하면 저장장치 구간을 건너뛰고 기존 RAM 데이터로 이어진다. 비교는 선택한 사건을 끝낸 뒤 제안하며 첫 재생을 방해하지 않는다.

## 6. 반응형·접근성·학습 보조

- **데스크톱:** 부품 중심을 화면의 약 60% 지점에 두고 왼쪽 빈 공간에 짧은 설명을 둔다. 관계가 넓어지는 구간만 전체 폭을 사용한다.
- **모바일:** 단순 축소 대신 대상은 상단 55%, 설명은 하단에 재배치한다. CPU↔RAM 관계는 가까운 부품에서 먼 부품으로 세로 이동한다. 버튼 최소 터치 영역은 44px로 잡는다.
- **입력:** 자연 스크롤을 기본으로 유지한다. 마우스 드래그는 캔버스 위에서만 진행한다. 키보드 방향키·PageDown·Space·하단 구간으로 같은 장면에 도달한다.
- **모션 감소:** 장면별 의미 있는 정지 구도로 바로 이동한다. 빠른 회전·줌 이동 없이도 제목·문장·방향을 알 수 있어야 한다.
- **보조 기술:** 현재 단계만 `aria-live`로 알린다. 매 프레임 수치나 데이터 표식을 읽어 주지 않는다. 상세 창의 포커스는 닫을 때 원래 버튼으로 돌아온다.
- **WebGL 대체:** 완성 구현은 동일한 구도의 대표 이미지·설명·단계 이동을 제공한다. 현재 모션 시안은 WebGL이 필요하며 실패 시 이를 명시한다.
- **검증할 이해:** 문장을 외우는 대신 “입력을 해석하는 곳 / 작업 데이터를 두는 곳 / 픽셀을 만드는 곳”을 본 뒤 구분할 수 있는지 확인한다. 기본 화면에 시험 패널을 추가하지 않는다.

## 7. 실제 구현으로 옮길 구조

`ScenarioFilm`이 공용 렌더러를 빌리고 `ScenarioTimeline.sample(progress)`가 `camera / focus / modelPose / event / frameState / caption`을 반환한다. 시나리오 내용은 데이터로 분리한다. 모델 생성과 경로 구성은 진입 시 한 번 하고, 진행 중에는 값만 바꾼다.

기존 `Experience.story()`의 단계별 모델 크기 축소·재배치와 재생 타이머를 이 연속 타임라인으로 교체한다. 기존 `#story/{id}/{step}` 주소는 해당 의미 구간에 매핑해 직접 링크와 뒤로 가기를 보존한다. 상세 창·컬렉션·부품 보기를 다녀오면 같은 진행도에서 복귀한다.

고정 메시 배칭, 공유 재질, 사전 셰이더 컴파일, 기기별 DPR 제한을 적용한다. 화면의 프레임 텍스처는 결과가 바뀔 때만 갱신한다. 장면에 없는 모델은 불필요하게 렌더링하지 않으며 정지·백그라운드 상태에서는 프레임 요청을 멈춘다.

**성능 목표:** 일반 데스크톱 60fps, 중간급 모바일 30fps 이상을 목표로 실제 기기에서 측정한다. 이는 아직 확인된 결과가 아니다. 성능이 부족하면 신호 효과·반사·그림자부터 줄이고 인과관계와 대상 크기는 유지한다.

## 8. 구현 순서와 통과 기준

1. 이 시안으로 구도·카메라 거리·드래그 감각·문장 밀도를 검토한다.
2. 클릭→화면을 먼저 완성한다. CPU 상태 변화, 명령 표식, VRAM 프레임, 주사 출력까지 연결한다.
3. 같은 입력·렌더링 구조에 부팅과 파일 열기를 추가한다.
4. 실내→네트워크→데이터센터로 규모가 바뀌는 검색 시나리오를 추가한다.
5. 실제 모바일·Safari와 접근성 대체 경로를 확인한다.

완료 조건은 “부드럽게 움직인다”만이 아니다. **앞 단계의 결과가 다음 단계의 원인이 되고**, 역스크롤이 같은 장면을 재현하며, 빠른 입력에도 목적 상태가 맞고, 첫 행동의 결과가 마지막 화면에 보여야 한다. 단계 경계의 카메라 불연속, 텍스트와 모델 겹침, 의도하지 않은 확대 반전, 프레임 시간을 기반으로 한 물리 속도 오해를 각각 확인한다.
