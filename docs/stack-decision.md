## 질문 1 — "애니메이션이 많으니 그에 맞는 언어"

### 전제부터 측정했다

"애니메이션이 많다 → 더 빠른 언어/런타임이 필요하다"가 참인지 실측했다.
브라우저에서 현재 코드의 프레임당 실제 작업 비용을 잰 결과:

| 작업 | 1회 비용 |
|---|---|
| `path.getPointAtLength()` (펄스 위치 계산) | 10.43 µs |
| `setAttribute('cx'/'cy')` | 0.93 µs |
| 카메라 transform 갱신 | 1.12 µs |

시나리오별 **한 단계 안의 최대 동시 펄스 수**는 실제로 이 정도다:

| 시나리오 | 단계별 펄스 수 | 최대 |
|---|---|---|
| boot | 0, 2, 2, 6, 3, 5, 4, 5 | 6 |
| game | 0, 4, 6, 3, 0, 3, 0, 6 | 6 |
| search | 0, 0, 4, 6, 5, 2, 3, 7 | **7** |
| storage | 0, 2, 0, 2, 3, 2, 4, 6 | 6 |

> **정정(2026-08-26).** 이 표의 초판은 boot 10 / storage 13 / 최대 13으로 잘못 적혀 있었다.
> 소스 집계 정규식이 여러 `flows` 블록에 걸쳐 잡힌 오류였다. 위 수치는 브라우저에서
> `kernel.pulseCount`로 단계마다 직접 읽은 실측값이다. **실제 최대는 7개.**

최대 부하(7개) 기준 프레임당 비용 = **0.080 ms**. 60fps 프레임 예산 16.67ms의 **0.48%**다.

> **60fps를 유지하면서 감당 가능한 펄스 수: 약 733개.** 현재 최대치의 **약 105배** 여유.

### 결론: 이 프로젝트의 언어 선택은 애니메이션 성능과 무관하다

병목이 존재하지 않으므로 "빠른 언어"라는 축 자체가 성립하지 않는다. WebAssembly·Rust는
물론이고 Canvas/WebGL 전환도 **얻는 성능이 0**이다. 따라서 언어는 다른 기준
— 오타로 인한 조용한 실패를 막는가 — 으로 골라야 한다.

### 그 기준으로 다시 고르면: **순수 JavaScript 유지 + `// @ts-check` 한 줄**

이 코드베이스의 대표 버그 3종을 실증했다. 다음은 전부 **예외도 경고도 없이 통과**한다:

```
stage.fit(['존재하지않는부품'])      → 예외 없음, 조용히 통과
stage.setStates({ lit: ['오타난id'] }) → 예외 없음, lit 0개 → 보드 전체가 dim 처리
stage.startFlow('없는배선')          → 예외 없음, 펄스 0개
stage.emphTraces([{id:'없는배선2'}]) → 예외 없음
```
콘솔 출력: **없음**. 특히 두 번째 — `lit` 배열에 오타 하나면 **화면 전체가 어두워지는데
아무 경고가 없다**.

**TypeScript 전면 전환은 이 버그들을 하나도 잡지 못한다.** `stage.add(id, comp)`의 id가
그냥 `string`이라, `focus: ['cpuu']`는 `--strict`에서도 완벽히 유효한 타입이다. 잡게
하려면 API를 재설계해야 하는데, 그 재설계는 JSDoc으로도 똑같이 된다. 반대급부로 빌드
단계가 생기고(무빌드라는 최대 강점 파기) tsc watch를 상시 띄워야 한다.

반면 `// @ts-check` 한 줄은 **0분 투자로** opts 키 오타를 잡는다. 이 머신의 tsc 4.9.5로
재현 확인:

```
RAM(700, 150, { h: 260, lableDy: -272 })
→ Object literal may only specify known properties...
   Did you mean to write 'labelDy'?
```

팩토리들이 이미 구조분해 기본값을 쓰기 때문에 TS가 타입을 스스로 추론한다. JSDoc 0줄로
된다. (`@param` JSDoc 80줄을 더 붙여도 추가로 잡는 건 인자 개수 실수뿐인데, 그건 이미
콘솔에 `<text> attribute x: Expected length, "NaN"`으로 시끄럽게 뜬다.)

**id 문자열 오타는 타입이 아니라 검증으로 잡는다** — 아래 `tools/check.mjs` 25줄.

## 실행 계획

### 1단계 — 지금 (약 1시간, 재작성 0줄)

수정 파일 4개 + 신규 1개. 시나리오 4개와 components.js 본문은 무수정.

0. `rm -rf .pytest_cache` (다른 프로젝트 잔재). **`git init` 금지 — 이미 저장소다.**
1. **`tweenTo` resolver 이월** (약 4줄) — `tween` 교체 시 대기 중 resolve들을 새 트윈으로
   carry. ⚠️ "이전 resolve를 먼저 호출"로 쓰면 **안 된다** — 카메라가 아직 움직이는데
   잠금이 풀려 '건너뛰기 방지'가 정확히 그 지점에서 깨진다.
2. **줌을 로그 공간에서 보간** (1줄) — `cam.s = s0 * Math.pow(s1/s0, e)`.
   배율은 지각적으로 로그 스케일이다. **체감 이득이 가장 큰 한 줄.**
3. **이징을 CSS와 통일** (1줄) — 대칭 cubic-in-out → ease-out 우세 `1-(1-t)^4`.
   `style.css`에 이미 `--ease: cubic-bezier(0.16,1,0.3,1)`가 있는데 카메라만 리듬이 달라
   부품 페이드와 어긋난다.
4. **거리 비례 duration** (약 3줄) — 이동량으로 ms를 550~1100 클램프.
5. **펄스 죽는 900ms 제거** (2줄) — `startFlow` 호출을 `await fit()` **앞으로**. 위 버그 1.
   flows는 완료 Promise와 무관하므로 위험 0.
6. `.comp.dim .blades { animation-play-state: paused; }` (1줄) — 위 버그 4.
7. `await st.run?.(stage)` (1줄) — 레지스트리 15줄은 만들지 말 것(호출자 0건).
8. **`lib/components.js` 1행에 `// @ts-check`** (1줄). ⚠️ `stage.js`에는 붙이지 말 것 —
   멀쩡히 도는 코드를 타입 체커 비위 맞추려 고치는 건 도구에 잡아먹히는 경로다.
9. **`tools/check.mjs` 약 25줄** — `stage.add`/`stage.trace`의 id 집합과 모든 step의
   `focus`/`lit`/`traces[].id`/`flows[].trace`를 정규식으로 대조. 미참조 정의 경고도
   포함(위 버그 5가 걸린다). `focus: null`은 정상이므로 오탐 금지. **CI 금지**, 손으로 실행.
10. `stage.js`의 `if (!t) return;` / `if (!c) return;` 위에 `console.warn` 3줄.
    ⚠️ **throw 절대 금지** — 위 버그 3 때문에 페이지가 굳는다.
11. 커밋.

**효과**: 사용자가 1순위로 밝힌 "애플 제품 페이지 같은 애니메이션"이 실제로 좋아지고

### 2단계 — 5번째 시나리오를 **현행 방식 그대로** 한 편 써 본 직후

저작 인프라는 그때 판정한다. 미리 짓지 않는다.

  컴포넌트 좌표인가, 배선 path인가, 라벨 좌표인가, 본문 텍스트인가.

  **끝점별 오프셋**. `trace()`는 영구 병행 유지. **기존 29개는 한 줄도 retrofit 금지.**
- `?step=N` 딥링크 (3줄) — ⚠️ 클램프 필수. `apply()`엔 `goTo()`의 범위 검사가 없어

- 키보드 접근 2건 (약 15분) — `li`에 `tabindex="0"` + Enter/Space, `:focus-visible` 아웃라인.
- Chrome·Safari DevTools Performance로 단계 전환을 녹화해 **실제로 프레임이 떨어지는지**
  먼저 확인. 떨어진다면 원인은 거의 확실히 `filter: drop-shadow`다.

## 채택하지 말 것 (흔히 권해지지만 이 프로젝트엔 해로운 것)

- **256샘플 LUT 펄스 최적화** — 66배 빨라지는 건 사실이나 *이미 한가한 프레임*에서 0.5ms를
  아낀다(트윈과 펄스는 겹치는 프레임이 하나도 없다). 대가는 확실하다: 트레이스 길이가
  36~1517px인데 1517px를 256샘플로 나누면 간격 5.93px이라, `search.js`의 90도 코너에서
  점이 배선에서 눈에 띄게 뜬다. **존재하지 않는 성능 문제를 고치며 1순위 제약을 위반한다.**
- **TypeScript 전환** — 대표 버그 3종을 `--strict`에서도 0개 잡는다.
- **런타임 검증기를 앱에 넣기, 특히 throw로** — 페이지를 열어야만 작동하고, throw는
  busy 래치로 화면을 굳힌다.
- **기존 트레이스 29개를 `wire()`로 retrofit** — 양끝이 정확히 앵커-앵커인 건 6개뿐이고
  나머지는 **의도적 오프셋**이다. `t_pcie16`(x=500)과 `t_dmi`(x=590)는 B앵커가 둘 다 560이라
  wire로 바꾸면 부채꼴 배선이 한 점으로 무너진다.
- **dagre/elkjs 자동 레이아웃** — "이게 실제 생김새다"가 학습 내용의 일부인데 계층 정렬이
  그걸 뭉갠다. 노드 하나 추가할 때마다 32개 step의 카메라 프레이밍을 다시 잡아야 한다.
- **Vite / Vitest / Playwright 지금 도입** · **React/Vue/Svelte/Solid/Astro** ·

## 미해결 질문

1. 1단계 적용 후 카메라가 실제로 "애플 같아졌는지"는 **눈으로만 판정 가능**하다. 너무 느리면
   이징 지수를 4→3으로 낮춰라 — 취향이라 정답이 없다.
2. 트윈 중 `filter: drop-shadow` 재래스터화가 실제 병목인지 **아직 아무도 측정하지 못했다**.
   보고된 수치는 전부 JS 실행 시간이다. Chrome·Safari 양쪽에서 녹화하기 전엔 처방을 넣지 마라.
3. 5번째 시나리오의 실제 병목이 배선 좌표가 아니라 **컴포넌트 팩토리 부재**로 판명될
   가능성이 상당하다. 카탈로그를 다 덮으려면 오디오 코덱·DAC·ISP·NPU·MMU/TLB·APIC·EC 등
   **팩토리 20~25개(약 350~400줄)**가 더 필요하다. 그렇다면 `wire()`보다 팩토리 확충이 우선이다.
4. **검증기도 타입도 "의미가 틀린 id"는 못 잡는다.** `search.js`에서 rack과 router를 바꿔 써도
   전부 통과하고, 카메라가 데이터센터 대신 집으로 줌인해도 도구는 침묵한다. "검증기를 넣었으니
   안심"이라는 착각이 오히려 위험하다.
5. `tools/check.mjs`의 정규식은 **id가 리터럴일 때만** 동작한다. 반복문으로 컴포넌트를 대량
   생성하고 싶어지는 순간(AI 행렬곱의 셀 격자 등) 조용히 무력해진다.

# 부록 — WebAssembly 구현 (2026-08-26)

위 보고서는 WASM이 불필요하다고 결론냈으나, 사용자 요청으로 실제 구현하고 측정했다.
**결론: 예측대로 오늘의 부하에서 체감 이득은 없다. 다만 확장 여유는 크게 늘었고,
정확도는 오히려 개선됐다.**

## 무엇을 WASM으로 옮겼나

| 계층 | 담당 | 비고 |
|---|---|---|
| **WASM** (`lib/cawiki.wasm`, Rust 545줄 → 41.9KB) | SVG path 파싱 · 3차 베지어 평탄화 · 호길이 균등 재샘플링 · 펄스 전진 · 카메라 이징/보간 · `fit()` 바운딩박스 수학 | 매 프레임 수학 **전부** |
| **JS** (`lib/stage.js`) | SVG DOM 구성, 속성 쓰기 | 계산 없음 |
| **CSS** | 상태 전환(lit/trail/dim), 글로우 | 무변경 |

렌더러는 **SVG 그대로**다. 벡터 선명도·한글 라벨·접근성 트리·CSS 상태 전환을 모두 지켰다.
Canvas/WebGL로 갔다면 이 넷을 전부 잃었을 것이다.

## 성능 실측 (같은 페이지에서 두 백엔드 나란히)

펄스 위치 계산만, DOM 쓰기 제외:

| 동시 펄스 | WASM | JS | 배율 | WASM 프레임예산 | JS 프레임예산 |
|---|---|---|---|---|---|
| **7 (현재 최대)** | 1.75 µs | 74.75 µs | **42.7×** | 0.01% | 0.45% |
| 50 | 4.75 µs | 349 µs | 73× | 0.03% | 2.09% |
| 200 | 5.50 µs | 1,395 µs | 254× | 0.03% | 8.37% |
| 733 | 10.0 µs | 5,036 µs | **504×** | 0.06% | 30.2% |

카메라 1스텝: WASM 0.435µs vs JS **0.400µs** — **JS가 미세하게 빠르다.**
계산이 사칙연산 몇 줄뿐이라 WASM 경계를 넘는 비용이 이득을 넘어선다. 정직하게 남긴다.

**해석**: 0.45% → 0.01%. 둘 다 사람 눈에 보이지 않는다. 실질 변화는
**60fps 한계 펄스 수가 약 733개 → 5만 개 이상**으로 늘어난 것뿐이다.

## 정확도 — 예상 밖의 실제 이득

브라우저의 `getPointAtLength`와 전 트레이스·전 구간 대조:

| 지표 | 값 |
|---|---|
| 전체 평균 오차 | **0.00006 px** |
| 최대 오차 | **0.0011 px** (줌 2.4배 환산 0.0027px) |
| 직선 경로(H/V/L) | **0.0000 px** — 완전 일치 |
| `t_ret` (1517px, 90° 코너 2개) | **0.0001 px** |

본문에서 "256샘플 LUT는 코너를 최대 3px 자른다"며 기각했던 그 위험이,
**0.5px 고정 간격 재샘플링**에서는 사실상 사라진다. 샘플 수를 고정하지 않고
**간격을 고정**했기 때문이다 — 경로가 길수록 샘플이 비례해 늘어난다
(`t_ret` 3035개, `t_ram1` 121개).

## 부수 효과

- **경고 3종 추가** — `fit`/`setStates`/`emphTraces`/`startFlow`가 알 수 없는 id를 받으면
  이제 `console.warn`을 낸다(throw 아님 — busy 래치 회피). 본문 1단계 항목 【10】이 함께 처리됐다.
- **`tweenTo` resolver 이월** — 커널 재배선 과정에서 자연스럽게 해소됐다(본문 【1】).
  대기 중 resolver를 `pendingResolvers`에 모아 트윈 완료 시 일괄 flush한다.
  ⚠️ 본문 경고대로 "이전 resolve 먼저 호출" 방식은 쓰지 않았다.
- **커널 배지** — 화면 좌상단에 `WASM`/`JS` 표시. `?kernel=js`로 폴백 강제 가능.
- **자동 폴백** — `.wasm` 로드 실패 시(파일 직접 열기 등) 조용히 JS 백엔드로 전환.

## 대가

| 항목 | 내용 |
|---|---|
| **빌드 의존성** | 수정하려면 Rust + `wasm32-unknown-unknown` 필요. **런타임은 무빌드 유지** — `lib/cawiki.wasm`이 커밋되어 `python3 -m http.server`로 그대로 열린다 |
| **코드량** | Rust 545줄 + `kernel.js` 201줄 = **746줄 증가** (기존 1,630줄 대비 +46%) |
| **디버깅** | 펄스 좌표가 이상하면 이제 Rust를 봐야 한다 |
| **전송량** | +41.9KB (로컬이라 무의미, Pages 배포 시 gzip으로 더 줄어듦) |

## 되돌리기

`?kernel=js`로 즉시 비교 가능하고, 완전 제거는 `lib/kernel.js`의 JS 백엔드만 남기고
`createKernel`이 항상 그것을 반환하게 하면 된다(1줄). `lib/cawiki.wasm`과 `wasm/`을 지우면 끝.

## 빌드

```
cd wasm && cargo build --release --target wasm32-unknown-unknown
cp target/wasm32-unknown-unknown/release/cawiki.wasm ../lib/cawiki.wasm
```

## 검증 결과

4개 시나리오 × 8단계 전수 실행: **오류 0, 경고 0**, 커널 펄스 수와 DOM dot 수 전 단계 일치.
입력 통제 회귀 없음 — 휠 25회 폭주 → 정확히 1단계, 쿨다운 중 관성 10회 흡수,
이후 의도적 스크롤 → 다시 1단계. `?kernel=js` 폴백도 8단계 전수 통과.
